# 阶段 1：系统骨架学习笔记

## 1. 本阶段目标

第一周的目标是完成 AI 眼镜实时视觉记忆助手的最小系统骨架。这个阶段不追求真实模型效果，而是先跑通完整工程链路：

```text
图片/问题输入 -> 模拟 OCR / 模拟 VLM -> 场景摘要 -> SQLite 记忆写入 -> 时间线展示 -> 关键词检索
```

本阶段完成后，项目已经不是一个零散 demo，而是具备后续扩展位的系统原型。

## 2. 和项目定位的关系

我们之前确定，这个项目要服务两个目标：作品集展示和实习准备。因此第一周不能直接堆模型 API，而要先建立工程结构。

AI 眼镜项目的核心不是“当前图片问答”，而是：

- 看见当前场景。
- 理解当前场景。
- 把场景变成记忆。
- 未来能检索这段记忆。

第一周实现的 memory event、SQLite 时间线和 pipeline，就是后续 OCR、VLM、ASR、RAG 的底座。

## 3. 我们在对话中确定的设计决策

- 主项目定为 AI Glasses Memory Assistant，也就是 AI 眼镜实时视觉记忆助手。
- 作品集采用“1 个主项目 + 1 个辅助项目”，不堆多个小 demo。
- 实习方向优先对齐 AI 眼镜 / 智能硬件 + 多模态 LLM 应用。
- 项目采用训练营式分阶段推进。
- 第一周只做系统骨架，不接真实 OCR、ASR、VLM 和向量数据库。
- 所有文档尽量使用中文，技术名词和代码标识符保留英文。
- 学习笔记要足够详细，能用于复习、博客、简历和面试。

## 4. 核心概念

### FastAPI

FastAPI 在项目中负责后端服务接口。它把 pipeline 能力暴露成 HTTP API，例如健康检查、提问、读取记忆、搜索记忆。

### Streamlit

Streamlit 负责第一版演示 UI。它不适合做复杂产品前端，但非常适合快速做可交互 demo，让面试官看到项目流程。

### SQLite

SQLite 是第一版记忆存储。它不需要单独部署数据库，适合本地 demo 和学习阶段。后续即使加入向量数据库，SQLite 仍然可以保存结构化时间线。

### Pydantic

Pydantic 用于定义数据模型和接口返回结构。它让 memory event 的字段更清晰，也方便 FastAPI 自动生成接口 schema。

### Memory Event

`memory event` 是系统“记住”的最小单位。一次用户提问和系统回答，会被保存成一条 memory event，包含问题、回答、场景摘要、OCR 文本、图片路径和延迟统计。

### Pipeline

pipeline 是业务流程编排层。它不关心 UI 怎么展示，也不关心 HTTP 怎么传输，只负责把一次视觉记忆交互串起来。

## 5. 技术原理

第一周的技术原理可以理解为一个分层架构：

- UI 层：负责用户输入和结果展示。
- API 层：负责 HTTP 接口。
- Pipeline 层：负责业务流程编排。
- Service 层：负责模拟 AI、延迟统计、记忆存储。
- Model 层：负责数据结构。
- Storage 层：负责 SQLite 持久化。

这种结构的好处是每一层职责清楚。后续接真实 OCR 或 VLM 时，只需要替换 service 实现，不需要重写 UI 和 API。

## 6. 工程实现

当前实现包括：

- `MemoryEventCreate`：创建记忆时使用的数据模型。
- `MemoryEvent`：已经写入数据库的记忆事件。
- `MemoryStore`：封装 SQLite 操作。
- `MockAIService`：模拟 OCR、VLM 和场景摘要。
- `LatencyTracker`：记录各阶段耗时。
- `MemoryPipeline`：串联一次视觉记忆交互。
- FastAPI 路由：提供 `/health`、`/ask`、`/memories`、`/memories/search`。
- Streamlit UI：提供上传图片、输入问题、查看回答、时间线和搜索。

## 7. 关键代码解读

`MemoryStore.add_event` 负责把一条 memory event 写入 SQLite。它会记录创建时间，并把 `latency_ms` 用 JSON 字符串保存。

`MemoryStore.list_events` 按时间倒序返回记忆时间线。这样最新发生的交互会显示在最上方。

`MemoryStore.search_events` 第一周只做关键词搜索，搜索范围包括问题、回答、场景摘要和 OCR 文本。

`MemoryPipeline.ask` 是当前最重要的业务函数。它依次执行模拟 OCR、模拟 VLM、模拟场景摘要、延迟统计和记忆写入。

## 8. 踩坑记录

第一周需要注意几个问题：

- 不要一开始就接真实模型，否则容易被 API key、网络、GPU 或依赖安装卡住。
- SQLite 存储路径需要自动创建父目录，否则第一次运行会失败。
- 中文文档需要用 UTF-8 读取和保存。
- UI 层不要写业务逻辑，否则后续很难测试。
- 模拟服务不是偷懒，而是为了先固定系统接口和数据流。
- 实际练习中，修改 `mock_ai.py` 里的模拟 OCR 文案后，页面一开始没有变化。原因有两个：第一，SQLite 时间线里已经保存的旧记录不会因为代码改变而自动更新；第二，运行中的 Streamlit 进程可能还在使用旧模块，需要重启 UI 服务。正确验证方式是重启 UI 后重新提交一个新问题，再看“本次回答”和最新时间线记录。

### 练习问题：为什么改了 `mock_ai.py` 里的文字，UI 没有反应？

排查结论：

- 文件已经保存，新 Python 进程导入 `MockAIService.run_ocr()` 时可以读到新文案。
- `data/memory.sqlite3` 里的旧 memory event 仍然保留旧 OCR 文本，这是正常现象。
- 旧记录是历史数据，不会因为代码变更而自动重写。
- 如果运行中的 Streamlit 没有重新加载模块，需要重启 UI。

这说明代码、运行进程和数据库历史记录是三件不同的事：

```text
mock_ai.py     决定之后如何生成新内容
Streamlit 进程 决定当前页面运行的是哪一版代码
SQLite 数据库  保存已经生成过的历史记录
```

## 9. 性能与优化

第一周虽然没有真实模型，但已经加入了延迟统计。这是为了从一开始培养低延迟系统意识。

后续真实系统中，延迟可能来自：

- OCR 推理
- VLM 图片上传和回答
- ASR 转写
- 向量检索
- 数据库读写

第一周先记录 `ocr`、`vlm`、`summary` 和 `total`，后续可以继续扩展。

## 10. 面试高频问题

### 你的项目为什么不是普通视觉问答 demo？

因为项目不仅回答当前图片问题，还会把场景摘要、OCR 文本、用户问题和系统回答结构化保存为 memory event，后续支持时间线浏览和历史检索。

### 为什么第一版使用 SQLite？

SQLite 不需要额外部署，适合本地原型和作品集 demo。它能稳定保存结构化时间线，后续可以和 Chroma 或 FAISS 配合使用。

### 为什么先用模拟服务，而不是直接接真实 VLM？

第一周目标是验证系统架构和数据流。模拟服务可以避免被模型依赖卡住，同时让 OCR、VLM、ASR 后续都能作为可插拔模块替换。

### pipeline 层有什么价值？

pipeline 把业务流程从 UI 和 API 中拆出来，使系统更容易测试、维护和扩展。后续接真实模型时，不需要改动界面层。
