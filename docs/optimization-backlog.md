# 优化 Backlog：系统跑通后再处理

这份文档记录暂时不打断主路线、但后续有价值的优化项。当前优先级仍然是先把完整项目链路跑通：

```text
手机摄像头 / 图片输入
-> OCR
-> VLM 问答
-> 记忆写入
-> 检索
-> Web 展示
-> 后续硬件端输入原型
```

## O1：OCR 识别速度优化

### 当前现象

本地 PaddleOCR 首次识别可能需要 10-30 秒。当前实测首次 OCR 约 24 秒，属于模型冷启动、CPU 推理初始化和模型加载导致的正常现象。

### 为什么先不优化

当前阶段的目标是证明真实 OCR 能接入视觉记忆 pipeline，而不是先追求实时性能。如果现在过早优化，容易把时间耗在模型压缩、推理后端和图像预处理上，影响后续 VLM、检索和硬件输入主链路。

### 后续优化方向

- 缓存 PaddleOCR provider，避免重复初始化模型。
- 对输入图片做尺寸压缩，降低 OCR 推理成本。
- 选择轻量 OCR 模型，而不是默认 server 模型。
- 将 OCR 初始化前置，在应用启动后预热模型。
- 在硬件端上传前做图像压缩和帧采样。
- 记录冷启动耗时和热启动耗时，单独分析性能。

### 后续验收标准

- 首次识别时间可解释、可提示。
- 热启动后单张普通图片 OCR 尽量控制在 1-3 秒。
- UI 中继续展示 OCR 延迟，方便演示性能变化。

## O2：外文 OCR 结果翻译成中文

### 目标

当摄像头或图片中出现英文、日文、韩文等外文文本时，系统可以把 OCR 结果翻译成中文，并在回答中使用中文解释。

### 为什么先不实现

当前主线还需要继续接真实 VLM、向量检索和硬件输入。如果现在加入翻译，会新增一个模型或 API 依赖，也会让 pipeline 的输出字段变复杂。更稳妥的做法是先把完整系统跑通，再把翻译作为增强能力接入。

### 后续设计方向

可以把翻译做成独立 provider：

```text
OCR 文本
-> LanguageDetector 判断是否需要翻译
-> TranslationProvider 翻译成中文
-> VLM / Summary / Memory 使用原文 + 中文译文
```

建议后续在 memory event 中增加字段：

```text
ocr_text_original
ocr_text_zh
detected_language
translation_provider
```

第一版可以不做复杂语言检测，只要 OCR 文本中明显包含外文，就调用翻译模块。

### 后续验收标准

- 英文图片可以展示原文 OCR 和中文翻译。
- 系统回答优先使用中文。
- 翻译失败时不影响 OCR 和记忆写入，最多显示原文。
- 翻译耗时单独记录到 latency 里。

## 当前决策

这两个优化项暂时不进入当前实现队列。当前继续推进主路线：

1. 已完成：Web MVP。
2. 已完成：手机摄像头 / 图片输入。
3. 已完成一部分：PaddleOCR 真实 OCR。
4. 下一步：接真实 VLM 或向量检索，让视觉记忆系统从 OCR demo 变成完整 AI 应用。
5. 等完整项目能跑通后，再回头处理 OCR 加速和外文翻译。
