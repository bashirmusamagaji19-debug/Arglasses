# Bug 11：轻量语义检索受重复记忆干扰

## 现象

在手机端和 VLM 调试过程中，多次拍照、重复提交同类问题后，历史检索有时会答非所问。

典型表现：

```text
用户问：刚才拿过什么？
系统可能召回不够相关的旧场景，或者被多条重复记忆影响排序。
```

## 排查过程

1. 先确认主链路可运行：手机端图片能上传，VLM 能回答，SQLite 能写入记忆。
2. 查看当前检索实现，发现它仍然是轻量语义检索：读取最近 memory events 后，用 question / answer / scene_summary / ocr_text 做规则相似度排序。
3. 这个方案没有 embedding，也没有真正的语义向量空间，因此对重复数据和长时间线比较敏感。
4. 继续上 Chroma / FAISS 前，如果没有记忆清理入口，后续向量索引也会被重复记忆污染。

## 根因

这不是单个 bug，而是当前阶段的工程边界：

- 轻量语义检索只能作为过渡方案。
- 重复提交会制造多条几乎相同的 memory event。
- 过长时间线会把低相关旧记录引入召回候选。
- 缺少记忆生命周期管理，用户无法清理错误或重复记忆。

## 处理方案

先加入记忆管理能力，而不是马上重写检索：

```text
单条删除
清空全部
只保留最近 N 条
精确去重
```

这些能力放在 `MemoryStore` 和 `MemoryPipeline`，同时暴露给 FastAPI 和 Streamlit UI。

## 二次问题：看起来重复但没有被去重

真实测试中出现过两条非常接近的记忆：

```text
问题：手上拿着什么
OCR：PaddleOCR：所得皆所顺 如意
回答 A：所得皆所愿
回答 B：所得皆所顺
```

用户视角下这两条来自同一张图、同一个问题，应该被当成重复记忆。但第一版去重规则使用：

```text
question + answer + scene_summary + ocr_text
```

这导致 VLM 回答只要有一个字不同，就无法命中重复 key。

修复后规则改为：

```text
有 OCR：question + ocr_text
无 OCR：question + answer + scene_summary
```

这样可以清掉重复拍摄 / 重复提交产生的近重复记忆，同时避免在没有 OCR 证据时误删不同场景。

## 为什么这样做

如果直接接 Chroma / FAISS，SQLite 和向量索引会同时存在。那时删除记忆不仅要删 SQLite，还要删对应 embedding。先把管理入口做出来，后续只需要在 pipeline 层补向量索引同步，不需要改 UI 和 API 入口。

## 面试复盘说法

> 我在测试轻量语义检索时发现，重复提交和过长时间线会干扰召回质量。这个问题不是简单调规则能彻底解决的，因为当前还没有真正的 embedding 语义空间。  
> 所以我先补了记忆生命周期管理，包括单条删除、清空、保留最近 N 条和精确去重。这样 demo 数据可控，后续接 Chroma / FAISS 时，也可以在同一个 pipeline 入口同步维护 SQLite 和向量索引一致性。
