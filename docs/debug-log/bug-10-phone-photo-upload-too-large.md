# Bug 10：手机拍照上传原图过大，PaddleOCR 被迫二次缩放

## 现象

使用手机页面拍照上传后，PaddleOCR 日志出现：

```text
Resized image size (4096x3072) exceeds max_side_limit of 4000. Resizing to fit within limit.
```

这说明手机上传的是 4096x3072 原图，后端保存后直接交给 OCR。

## 排查判断

问题不在 PaddleOCR 本身。PaddleOCR 的日志只是说明它收到了过大的图片，然后内部做了一次缩放。

更合理的处理位置应该在上传保存阶段：

```text
手机拍照原图
-> 后端上传入口统一压缩
-> 保存较小 JPEG
-> OCR / VLM 共用压缩后的图片
```

这样 OCR、VLM、存储和后续 RK3588 上传链路都能受益。

## 处理方式

1. 在 `save_input_image()` 中读取上传字节后，优先用 Pillow 压缩为 JPEG。
2. 默认最长边限制为 `1600`。
3. 压缩失败时保留原始字节，避免上传流程崩溃。
4. 将 `pillow>=10.4.0` 放入运行依赖和 `requirements.txt`。
5. 添加测试验证 4096x3072 手机图片保存后最长边不超过 1600。

## 验证

测试先失败：

```text
assert 4096 <= 1600
```

修复后聚焦测试通过：

```text
4 passed
1 passed
```

## 面试可讲点

- 多模态系统里图片尺寸是端云协同的关键工程问题。
- 不应该让每个下游模型各自临时处理原图，而应该在输入边界统一预处理。
- 上传阶段压缩能同时降低 OCR 延迟、VLM token/带宽成本和存储压力。
- 端侧 RK3588 后续也应该做类似的帧采样和图像压缩，再上传后端。
