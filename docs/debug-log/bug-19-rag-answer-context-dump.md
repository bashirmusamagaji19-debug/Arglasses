# Bug 19：RAG 回答像上下文拼接而不是自然问答

## 现象

历史记忆问答已经能完成 RAG 闭环，但用户问：

```text
鼠标是什么颜色的？
```

系统回答类似：

```text
根据历史记忆，最相关的一次记录是：...

相关记忆：
- ...
- ...
- ...
```

这能证明检索到了上下文，但用户体验更像“把上下文 dump 出来”，不是一个助手在直接回答问题。

## 排查过程

1. 检查 `RuleBasedRAGAnswerProvider`，发现它直接取第一条 memory 的 `answer`，再拼接 top-k 记忆摘要。

2. 对照目标输出，理想回答应该先直接回答：

```text
根据历史记忆，鼠标主要是黑色的；另外也出现过银灰色的鼠标。
```

3. 加回归测试覆盖“鼠标颜色”场景，要求：

- 回答以“鼠标主要是黑色”开头。
- 多条记忆里出现银灰色时要合并说明。
- 不再出现“最相关的一次记录是”和“相关记忆”这类上下文拼接标题。

4. 第一次实现颜色提取时，把“白色桌面”误判成鼠标颜色。继续收窄规则，只采纳颜色词靠近“鼠标”的短片段，例如：

```text
黑色无线鼠标
银灰色扁平鼠标
```

## 根因

RAG 的 generation 层不应该只是展示 retrieval 结果。对于用户问题，尤其是“颜色、位置、数量”这类追问，生成层需要从召回上下文中抽取关键信息并合并回答。

## 修复

1. `RuleBasedRAGAnswerProvider` 增加颜色问题识别。

2. 从 top-k memory 的 question / answer / scene_summary / OCR 中提取靠近“鼠标”的颜色词。

3. 生成更短、更直接的回答：

```text
根据历史记忆，鼠标主要是黑色的；另外也出现过银灰色的鼠标。
```

4. UI 仍然保留“使用的历史记忆”列表，作为可解释性证据。

## 面试复盘说法

> 我做完第一版 RAG 后发现，系统虽然完成了 retrieval -> context -> answer 的链路，但回答像在 dump 检索上下文，不像真正的问答助手。  
>  
> 所以我针对视觉记忆里常见的属性追问做了一层轻量 generation 逻辑：比如用户问“鼠标是什么颜色”，系统会从召回记忆中抽取靠近“鼠标”的颜色词，合并成一句自然回答，同时保留被使用的历史记忆列表作为可解释性证据。这个改动体现了 RAG 不只是向量召回，还需要把召回内容转成用户可用的答案。
